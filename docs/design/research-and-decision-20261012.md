# MeetingOS 尽调、设计选择与第一版范围

2026-10-12。依据用户最初的两个场景，以及本轮“充分尽调、定方案、开始开发”的授权。

## 结论与产品定位

把 MeetingOS 从“挑大咖聊天、会后生成纪要”改为**会中决策与客户辅助工作台**。人类直接使用网页，个人 Agent 是可选的协作者；网站默认保存资料和记录。先做好内部工具，个人账号隔离，授权限定到会议。

核心任务不是展示许多人物头像，而是让人在形成承诺和安排工作之前，看见风险、事实依据和下一步追问。客户会谈的主工作区是我方私有智囊；另开共享会议展示，只显示允许共享的记录。

这个决定来自此前实际复测发现的问题：上下文丢失、原稿保存不完整、修订不进入总结、Agent 写入不出现在网页、无用户和权限边界，以及移动端操作溢出。详见 [复测报告](../product-retest-20261012.md)。

采用官方源码、官方协议和项目维护者发布的 UI 图片；没有把营销文案当成功能验收。调查日期为 2026-10-12，源码固定到下列提交。

| 参考 | 实际查看的证据 | 值得借鉴 | 不直接照搬 |
| --- | --- | --- | --- |

Meetily 的分栏源码包含 `min-width:0/min-height:0`、移动端页签和可键盘操作的分栏；转写分页默认100条，并使用请求 ID 防止旧响应覆盖新会议。数据库原文不应该受模型上下文窗口的限制。这些是实际读到的实现依据。

LiveKit 的视图源码分别读取会话 `isConnected` 和 Agent `isConnected`，显示等待 Agent 与正在监听等状态。这说明“录音开启”与“AI 真能提供建议”必须分别表示。

Otter、Granola、Teams 支持网站请求被本云环境代理以403拒绝；相应官方域名已加入环境草稿，尚未发布。因此本轮**没有测试这些商业产品的最新登录界面、付费能力或响应表现**。本决定基于可核实的开源实现、协议和现有产品的实际复测，不是伪装成商业产品全面横评。

## 三个方向与选择理由

本轮生成并比较了三个独立视觉方向：浅色工作台、深色客户智囊、暖色笔记本。选择第一张 [浅色工作台参考图](meeting-workbench-reference.png)。

| 方向 | 优点 | 代价 | 决定 |
| --- | --- | --- | --- |
| 浅色工作台 | 同事容易上手；记录和建议同时可见；适合白天办公室/客户现场 | 多个状态和控制需要明确层级 | **采用** |
| 深色客户智囊 | 集中关注即时回答，适合个人沉浸使用 | 不利于统一内部会议与共享展示；现场亮光环境可读性需更多验证 | 暂不作为默认主题 |
| 暖色笔记本 | 记录体验亲切、阅读舒适 | 容易把产品做成事后笔记，弱化会中决策与 Agent 状态 | 不采用主方向 |

视觉参考图是方向草图，里面的参会人数、历史会议和风险内容不是已保存的真实数据。实际应用从空状态开始，不预填虚构风险或会议；验收截图中的数据是专门创建的合成测试数据。

## 定下来的 UI 与交互

桌面三个固定区域：约248px会议导航、可滚动记录区、持续可见的私有建议区。主要操作用蓝色，其余控件尽量克制。记录正文14px，建议13px，明确的标题、时间、类型、共享/私有标识。

- 左侧：新建、搜索历史、恢复会议、Agent授权、当前账号。
- 上方：会议标题、模式、实际保存/同步状态、设置、共享展示、内部导出。
- 记录区：记录/资料/总结三页签；原文和修订保留；文字输入与开始/暂停收音持续可达。
- 智囊区：选择助手、实际配置状态、自动建议开关、流式回答、引用依据、人工确认决定、快捷风险审查/追问。
- 390px手机：隐藏可展开的会议导航，记录与智囊切换；底部操作仍可见。768px使用页签避免拥挤双栏。
- 对话框：原生表单、可见焦点、Escape关闭、焦点限制与返回。图标采用已有标准图标库，隐藏装饰图标的无障碍名称。

没有照搬草图中的虚构人物头像、未实现的参会人数或风险等级。收音放在输入区，方便与手动补充一起使用；设置和模型状态是针对真实功能增加的控制。

### 内部会议

建会 → 填目标/预算/限制 → 上传资料 → 记录讨论 → 自动或人工检查计划 → 查看引用 → 人工修订并确认决定/行动项 → 总结与导出。

### 客户辅助

会前放客户需求和产品资料，私有字段放报价/交付底线 → 记录客户提问 → “帮我回答” → 私有区查看建议回答、依据、需核实问题 → 人工决定怎样回答 → 需要时另开共享展示/客户版导出。

### Agent 参与

网页创建到期、可撤销、可限定会议/权限的令牌 → 安装 Hermes Skill → Agent读取简报、资料、分页记录与事件变化 → 将自己的模型建议写为私有 advice → 网页立即可见 → 人工确认决定。

## 数据与权限设计

采用 Node24原生 SQLite，单实例内部部署。账号、会话、会议、事件、修订、文件原件、变化流和总结缓存共用一个数据库。原始记录不按200条裁切；模型请求预算与存储容量分开。

事件稳定 ID 用于重试幂等；修订必须携带当前 revision，避免两方覆盖。每次有意义的上下文变化增加版本，总结按版本/模型/受众缓存。修订总结会清除其缓存映射。

人类用 HttpOnly Cookie；Agent令牌只保存哈希，首次显示原文。检查账号、会议范围、作用域、有效期；撤销关闭已有事件流、语音连接和在途模型请求。客户投影由服务器生成，去掉私有文本及旧原文/引用元数据，避免仅在CSS里隐藏。

AI建议默认私有。形成共享决定需要人类明确确认。自定义Agent令牌不能将私有记录直接改公开。资料上传界面明确为共享资料；敏感谈判底线应放私有约束，不要混在共享附件里。

完整上下文包括简报、允许的私有约束、资料、修订后发言、确认决定及此前建议。单次输入超过160000字符明确报错；全量原文仍保留。没有悄悄裁切后声称“读完全部会议”。

## 第一版已实现与保留的边界

已实现上述网页/REST/SSE链路，以及有鉴权的语音WebSocket入口。模型缺失或失败明确提示，记录功能继续工作；没有模板兜底伪装真实AI。自动建议在新发言之后去抖触发，人工求助优先于自动分析。

第一版一个当前助手自动参与，其他助手可切换后人工求助；尚未实现多模型并行自动争论。保留25个预设助手/思维视角，作为紧凑选择器；不是默认铺满会议桌。实际网关模型ID可配置，历史默认型号没有验证可用性。模型“已配置”只说明凭证存在，真实推理成功与质量需另外验收。

尚未完成的内容：

1. 真实国外模型的质量、网络可达性、成本和延迟，真实麦克风识别、说话人自动区分及系统音频采集。
2. 组织共享/多同事同会成员权限。当前会议按账号隔离，Agent随账号授权；共享展示需该账号登录。
3. 个人Agent存储的自动双向镜像、完整OAuth/MCP授权服务器。
4. 超长会话的检索/分层压缩、OCR、后台持久任务、多实例推送、离线队列、音频归档。
5. 旧JSON会议与旧培训模块的数据迁移。新平台使用独立 `meetingos.sqlite`，不自动读取或修改旧数据库；部署前应做专门迁移与回滚演练。
6. 邮件、思维导图、人物声音、旧培训/答辩等旁支模块本版不接入新主入口，历史源码完整保留供后续决定。

这些边界不阻止第一版内部工作台开发/测试，但不能把本轮构建称作已经完成生产客户场景验收。

## 验收方式与后续顺序

先验证持久化/权限/上下文/实时同步，再验证实际桌面与手机操作。模型协议用受控本地网关测试，截图明确是合成数据；不把它当真实模型质量结果。详细执行证据在 [验证记录](../implementation-validation-20261012.md) 与根目录 `design-qa.md`。

后续先用真实模型和真实会谈做小范围试用，目标为求助开始后尽快出现首字、自动建议不打断讨论；延迟指标需要实测后定值。再完善多人共享与大会议上下文，最后单独安排部署。SSH和生产发布仍按用户此前决定暂停，其他服务器项目没有操作。
