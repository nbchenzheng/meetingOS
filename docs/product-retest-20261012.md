# MeetingOS 重新测试：按最初产品目标评估恢复版本

2026-10-12 · 测试对象：`source-snapshots/local-20261011/ai-board`

## 结论与建议

**这份版本已经有会议助手的基础框架，但尚未可靠实现“会中参与决策”和“客户谈判中的私有智囊”。它可以作为继续开发的起点。**

这次实际打开了页面，操作准备、发言、收音错误、纪要、总结、返回、编辑、导出、自定义角色、自动发言和附件失败流程，并检查了移动端、匿名接口及外部客户端写入。保存了 **23 张实际浏览器截图**，执行了 **19 个现有单测和 28 项隔离接口检查**。

最影响你原始目标的缺口是：

1. **AI 上下文不完整。** 简报中的预算约束没有进入角色请求；轻量点评连上传资料也没有读取。这个版本的角色请求也没有带入前面 AI 的观点。
2. **记录、修订与总结没有形成可靠链路。** 转写可能在重启时丢失；人工纠错不进入保存和导出；总结会过滤掉服务端保存的发言，还会长期复用同一会议的旧缓存。
3. **实时建议不等于即时回答。** 自动发言使用上一轮发言状态选人；各类建议有不同的关键词和定时门控，客户每次提问不能得到可靠响应。
4. **人类与外部 Agent 没有共享的受控工作流。** 匿名客户端能读写，但没有身份、授权范围、撤销机制或个人隔离；外部客户端写入转写后，人类页面看不到它。
5. **客户辅助界面尚未形成。** AI 意见出现在普通时间线中，没有独立的私有建议、我方／客户身份、可直接说出口的回答和事实出处流程。

建议优先修通会议上下文、保存恢复、版本化修订和共享事件，再围绕两个场景调整页面。名人角色选择可以保留为高级选项；首屏应先帮助同事开始工作。

### 3.2 准备页：流程清楚，工作目标不够突出

![会议准备及资料上传](evidence/retest-20261012/screenshots/02-preparation-filled.png)

**已有优点：** 标题、简报、角色和附件四步清楚；选中角色有轮廓和勾选反馈；未选角色时明确说明不能进入；文件有移除和大小提示；16MB 文件会在进入前被拦截，没有创建会议。

**主要问题：** 首屏同时展示 22 个模型／名人选择，优先让用户思考“选谁”，而你真正的任务是“审查计划”或“辅助客户会谈”。首次用户还无法判断这些角色的真实模型、可用状态、费用和上下文是否准备好。手机准备页本身没有横向溢出，但角色变成很长的单列列表，开始会议的按钮在下方。

建议先选场景，提供默认参会助手与可修改配置。高级区域再展开模型和名人视角。简报应结构化为目标、已知事实、限制和希望审查的决定，并明确告知哪些内容会给 AI。

**重要的承诺落差：** 页面称简报“将作为大咖发言的背景”，实际请求没有该简报。这需要修正数据链路；只改文案不能完成你的目标。

### 3.3 会中：操作很多，及时建议的位置不够直接

![会中界面](evidence/retest-20261012/screenshots/03-meeting-empty.png)

**已有优点：** 开始／停止收音比较醒目；能区分人类转写和 AI 发言；标签、搜索、导出及单角色手动发言已有入口。统一的暗色界面有基本一致性。

**主要问题：** 在 1440px 桌面宽度下，“准备”和“结束会议”已经出现竖向断字。底部角色卡主要展示头像、身份和状态，占用约数百像素；实时转写和建议需要争取这些空间。麦克风错误时，页面宽度由 1440px 撑到 1752px，搜索与导出被推到右侧。

默认显示“发言区”，主动点评却在“智能纪要”里。用户盯着当前发言时，不容易注意到后台产生的新建议。没有一处明确的输入区让用户写下“这个客户问题怎么答”或“这个计划有没有风险”。麦克风不能用时，只能点击通用角色发言或改简报，缺少手动输入当前会议内容的替代路径。

建议桌面采用“转写／讨论为主、当前建议固定可见”的布局，把参会助手收成紧凑列表。主操作区保留开始／停止、立即求助、场景与连接状态；搜索、标签、导出进入次级操作。

### 3.4 状态说明与错误恢复需要真实反映过程

未生成总结时就显示“已生成会议总结”（截图 07）；智能纪要页在未收音、没有请求进行时显示“AI 整理版生成中”（截图 06）。会议标题旁的 `LIVE` 在麦克风关闭时也一直出现，没有说明它指会话、收音还是 AI 正在工作。

建议分别显示收音、转写连接、模型请求和保存状态：未启动／等待输入／处理中／成功／失败／降级。兜底文本可以保留，但应与真实 AI 回复分开显示，给出可操作的原因与重试路径。

附件失败的提示能指出文件名，值得保留。不过页面称“会议已创建，可移除问题附件后重新进入”，实际重试会再创建一场会议。模拟 503 中，第一次失败后创建数为 1，移除附件重试后变成 2。应保留当前会议 ID 并重试上传，或在失败时回滚创建。

### 3.5 纠错与导出：看起来保存，实际仍用旧内容

![页面显示的纠错结果](evidence/retest-20261012/screenshots/14-transcript-edited.png)

测试把“客户要求一周部署”改成“客户要求三周部署”。页面显示修改后的内容和“已编辑”，但后端及下载的 TXT 均保留“一周”，没有“三周”。[纠错证据](evidence/retest-20261012/browser-edit-results.json)。

对你的场景，这会直接导致 AI 按过时事实建议，也会把错误承诺带进后续记录。建议编辑生成新的条目版本，写回服务端；后续 AI、导出和总结都读取明确的版本。标签、改名、收藏、忽略等目前主要也在组件状态中，不能把界面操作直接视作持久保存。

### 3.6 移动端与无障碍

![390px 视口中的会议页面，图中包含实际溢出的区域](evidence/retest-20261012/screenshots/16-meeting-mobile-without-error.png)

在 390×844 视口下，未显示错误时页面滚动宽度仍为 646px；显示错误时达到 1020px。收音模式和自动发言部分在视口外，角色卡横向挤压，转写区域所剩空间很小。截图保留了实际溢出内容，不代表手机能够同时看到整个宽度。

键盘和语义检查还确认：

- 准备页 22 个角色卡的可键盘聚焦数量为 0；键盘用户无法完成必须的角色选择。
- 自动发言用可点击 `label` 实现，没有 `input`、角色语义或可聚焦入口。
- 准备页标题／简报没有关联 `label` 或显式 `aria-label`，主要依靠占位说明。
- 折叠简报最大高度为 0，但内部两个输入仍可聚焦，没有 `inert`／`aria-hidden`。

见 [语义检查记录](evidence/retest-20261012/accessibility-results.json)。页面的原生按钮、部分标签页语义和附件错误 `role=alert` 是已有基础；浅色小字、焦点管理和自定义弹窗仍需改进。截图不能证明整体对比度合规；本次没有完整屏幕阅读器或 WCAG 验收。

## 4. 核心场景一：AI 在安排工作之前参与决策

### 4.1 完整上下文尚未成立

用三份独立信息验证输入：

| 信息 | 位置 | 是否进入角色发言请求 |
|---|---|---|
| `BRIEF_ONLY_LIMIT_120K`：预算上限 12 万元 | 项目简报 | **没有** |
| `DOC_ONLY_DEPLOY_3W`：部署最短三周 | 上传 TXT | 有 |
| `TRANSCRIPT_ONLY_PROMISE_14W`：计划成本 14 万元并承诺一周 | 转写 | 有 |

Claude 和 GPT 路由均出现上述结果；前一个 AI 的 `LOCAL_OPINION_MARK` 也没有进入下一次角色请求。见 [模型请求证据](evidence/retest-20261012/model-request-evidence.json)。这证明输入缺口，不能据此评价真实模型是否聪明或能否提出更好策略。

独立轻量点评的请求只有转写和有限 `ctx`，没有从会议读取简报或上传资料。该返回值没有写进 `meeting.commentaries`。同一会议因此有不同的 AI 输入与保存路径。

应建立统一会议上下文：目标、约束、附件事实、完整事件、滚动摘要、AI 已提意见、已确认决定和未决问题。内部会议尤其应在“决定／承诺”提交之前，让 AI 检查预算、工期、责任和证据冲突。

### 4.2 自动发言有路径，但选人会落后一轮

![两次合成提问后的自动发言](evidence/retest-20261012/screenshots/20-automatic-ui-synthetic.png)

开启自动发言后输入第一条带“方案”的合成问题，发给 `auto-speakers` 的 `transcriptText` 是空字符串。隔开调用门控再输入第二条问题时，请求只包含第一条，之后才发起 GPT 的自动发言。[自动发言请求记录](evidence/retest-20261012/automatic-ui-results.json)。

原因是 `addHuman` 更新 React 状态后立即调用 `maybeAuto`，后者读取的 `entriesRef` 尚未包含新条目。选人依据因此落后；角色真正发言时后端可能已收到后续转写，但这不能弥补当下触发遗漏。

此外存在不同机制：

| 路径 | 当前条件／间隔 | 对目标的影响 |
|---|---|---|
| 前端自动发言 | 关键词选人；调用至少间隔 1.5 秒；同角色 60 秒限制 | 首轮内容缺失，短时间后续问题可能跳过 |
| 后端大咖点评 | 最少 60 秒；另有 4.5 分钟门控、话题信号及单会议 20 条限制 | 一次提问之后的新问题不保证触发 |
| 前端轻量点评 | 150 秒周期；话题变化补采，60 秒门控；需正在收音 | 周期点评无法代替立即求助 |
| 智能整理／导图 | 正在收音时，分别 60 秒／5 分钟 | 缺少“现在整理”的手动路径 |

隔离测试中后端确实生成了第一条自动点评，但紧接的新问题没有增加点评。建议把“周期总结”“主动发现风险”和“用户立即求助”分成明确路径，人工求助优先执行，避免被周期节流压住。

### 4.3 总结输入与缓存会掩盖实际讨论

服务端转写只保存 `id/text/final/ts`，没有 `type` 或 `speaker`。总结服务仅接收 `type:speech/opinion` 的内容。实际捕获到的总结请求写的是“无转录内容”，没有测试发言校验词；在**新的独立会议**中补上 `type:speech` 后，发言才进入提示。这排除了旧缓存干扰。

角色意见保存于 `opinions`，总结页主要读取 `meeting.transcript`，没有合并这些意见。仅有 AI 发言的流程中，点击总结得到“尚无转录内容”。这会遗漏会中 AI 的讨论成果。

本地版总结缓存只按 `meetingId`，修订相同会议内容后返回 `cached:true`，没有新模型请求。它比服务器后续版本的缓存实现更早。应按会议事件版本、总结级别和实际输入建立缓存，修订／补充发言后失效。

## 5. 核心场景二：带 AI 见客户

当前只能复用会议流程，尚没有“客户辅助”工作方式。主要缺口如下：

| 客户现场需要 | 当前问题 | 建议行为 |
|---|---|---|
| 知道是谁提出问题、谁作出承诺 | 人类转写统一归为“麦克风”；改名是共享的人类标签 | 标注客户、我方及未知身份；允许纠正并保存 |
| 立即得到一句可用回答 | 只有角色“发言”，没有指定当前问题 | 选择问题后“建议我怎么回答”，优先短回答 |
| 避免承诺超出产品能力／底线 | 会前约束不进统一上下文 | 维护产品事实、报价权限、交付下限和待核验项 |
| 看懂回答从哪里来 | 通用建议缺少可核对的资料出处 | 回答附资料片段／版本／原转写锚点，标明不确定性 |
| 私有策略与展示记录分开 | 普通时间线直接显示 AI 身份和意见 | 私有建议区与可展示记录区分离，导出有明确范围 |
| 同时关注客户与电脑 | 顶部挤压、角色卡占空间、建议在另一个标签 | 一个固定、紧凑的建议区；快捷求助与隐藏操作 |
| 断网／模型失败时仍能继续 | 没有直接输入文字和可靠待同步记录 | 保留原稿，明确离线状态，连接恢复后补同步 |

网页目前主要输出文字，没有证明会自动对客户播放 AI 发言；这适合默默提供帮助。但如果客户看到屏幕或用户分享了整页，AI 卡片和内部意见会可见。单靠“带电脑做纪要”不能保证私有建议不可见。

建议客户模式的卡片区分“建议回答”“我方内部策略”“风险与需要核实”，并明确哪些字段可进入客户版纪要。客户模式的质量验收应检查错误承诺、没有出处的事实和不确定性表达，而不只是检查接口返回文字。

## 6. 人类与 Agent：接口可访问，产品级接入尚缺

### 6.1 人类入口已存在，历史与恢复不足

没有个人 Agent 的同事能在浏览器选择网站助手并开始会议，这是可以保留的方向。当前没有登录入口；创建、读取和修改会议均可匿名完成，会议对象没有用户／工作区归属。

浏览器刷新回到默认准备页，没有恢复原会议；从总结返回也重新初始化空时间线。会议列表和独立转写 GET 返回 404，前端没有历史列表／稳定会议 URL。即使服务端存在记录，人类仍缺少找回与继续的路径。

### 6.2 外部 Agent 能操作一部分信息，但没有受控权限和完整发现

匿名 API 可创建会议、读取简报与资料、更新标题、上传资料、请求发言和导出。发言接口甚至接受没有加入该会议的角色。WebSocket 不需要授权即可写入合成转写。

但这份主服务及前端没有人类登录、OAuth、作用域令牌、Agent 身份、可撤销授权、MCP 或 Hermes Skill。没有会议列表意味着 Agent 也缺少完整的信息发现入口；将 SDK 操作说明写成 Skill 不能替代服务端授权。

仓库里的培训数据模块包含用户／webhook 字段，但当前会议主入口没有导入它，不能据此认定会议网站已有用户隔离或同步。

### 6.3 人类与 Agent 没有同步到同一条可恢复时间线

第二个匿名 WebSocket 客户端发送 `AGENT_ONLY_NOTE`：服务端会议详情含有该内容，人类当前页面仍显示“全部 0”和空时间线。[同步检查](evidence/retest-20261012/agent-live-sync-results.json)。

![外部客户端写入后，人类页面仍为空](evidence/retest-20261012/screenshots/23-agent-write-not-visible-to-human.png)

WebSocket 当前主要负责上行转写与推送点评；人类 Hook 没有初始回放，也没有消费普通转写的共享事件。恢复点评的 GET 路由还有形状错误：返回 HTTP 200，但顶层是 `ok/meeting`，不是前端期望的 `commentaries/commentaryEnabled`。只检查 HTTP 状态会漏掉这个问题。

建议统一事件流，给每条事件确定 ID、序号、参与者、类型和版本；浏览器和 Agent 都从同一记录回放并订阅增量，重连按序号补拉。

### 6.4 自定义角色不能等同于接入自己的 Agent

“新建大咖”填写的是姓名、头衔、关注点、头像和颜色，属于网站内的提示角色，不会连接 Hermes 或个人 Agent。创建后卡片出现在当前会议，但服务端 `roleIds` 没有加入该角色；角色却进入全局角色库，在后续准备页可见。[角色检查](evidence/retest-20261012/custom-role-results.json)。

需要分别表示“站内 AI 助手配置”和“经授权接入的外部 Agent”，并在服务端保存会议参与者。早期可以先提供一个内部工作区；个人隔离和更多组织结构之后扩展，避免一开始就要求同事必须拥有 Agent。

## 7. 信息保存、同步与数据可靠性

| 本次检查 | 实际结果 | 对你使用的影响 |
|---|---|---|
| 纯转写后重启，期间没有其他保存操作 | 转写数量 1 → 0 | 刚讨论的内容可能丢失 |
| 转写后更新会议标题再重启 | 转写保留 | 其他写操作会顺带保存，不能依赖这种偶然条件 |
| 相同客户端转写 ID 重试 | 条目数 1 → 2 | 重连／重试会重复记录和影响 AI |
| 提交 201 条转写 | 仅保留 200 条，首条变成 `long1` | 原文被删除，不只是模型上下文截断 |
| 空白转写 | `200, ok:true, entry:null` | 调用方无法仅按成功字段判断已保存 |
| 人工纠错 | 页面变了，服务端和导出没变 | 事实修正无法传播 |
| 轻量点评 | 有返回，会议点评数量未增加 | 离开后不能按同一会议恢复 |

对照 [接口结果](evidence/retest-20261012/api-results.json)。不要直接把这份旧后端覆盖服务器版本；服务器已有部分后续持久化修正。

对于你提出的保存选择，建议默认由 MeetingOS 保存会议记录，让没有个人 Agent 的同事也能使用。个人 Agent 同步作为可选接入：授权读取或写入指定会议，支持完整导出以及有版本的增量同步。用户可以选择是否同步附件和私有策略；与 Agent 的记忆存储交互要有确认、重试与去重规则。

## 8. 值得保留的实现

不需要仅因为是早期版本就推倒全部代码。已有 React 页面、角色卡、流式发言时间线、WebSocket 上行、TXT 解析、文件大小守卫、错误提示、搜索／标签／导出入口和总结面板，都能作为后续基础。

本地版结构化纪要还通过了来源校验：模拟响应中的合法 `sourceEntryId` 被保留，编造的 ID 被移除。这个方向符合“有依据的 AI 建议”。不过导图的来源锚点没有保留：模拟网关返回有效 `entryIds`，API 输出仍丢掉它；`mindmap()` 归一化时没有传入有效 ID 列表。需要把设计接通，不能仅以字段或文档存在认定功能完成。

## 9. 改进优先级及首轮开发范围

### P0：让会议数据和 AI 输入可信

| 改进 | 要解决的具体问题 | 验收标准 |
|---|---|---|
| 确认统一开发基线 | 本地源码与服务器修正分叉 | 明确保留的后端修正与前端接口，不能因接回源码退回数据行为 |
| 统一会议事件、保存和回放 | 类型缺失、重试重复、200 条截断、重启丢失 | 原文完整；重复 ID 幂等；刷新／重启／重连可恢复 |
| 统一上下文构造 | 简报、资料、AI 意见在不同路径缺失 | 每类 AI 请求包含当前目标、约束和允许的资料；有输入版本记录 |
| 修订写回并更新下游 | 纠错只在页面，总结使用旧缓存 | 页面、API、导出、AI 与总结读到同一已确认版本 |
| 真实模型状态 | 角色存在，但运行时可能返回兜底 | 显示实际路由与成功／失败／降级；缺配置时不伪装成功 |
| 内部受控入口与权限基础 | 任意匿名客户端读写 | 内部入口受控；人类与 Agent 的访问范围在服务端执行 |

### P1：完成两个核心场景的最小可用流程

内部会议提供默认助手、实时建议区和“立即审查计划”。把发言与承诺关联到预算、工期、负责人及依据；结束后得到可确认的决定与待办。

客户模式提供客户／我方身份、会前事实与底线、指定问题的短回答、出处、风险以及私有建议区。资料准备、当前求助、结果展示都要能在普通笔记本和手机上操作。

同时补会议列表和稳定 URL、手动文字输入、附件失败重试、正确的摘要状态、紧凑角色选择、键盘操作以及真实更新的自定义参会名单。

### P2：扩展个人 Agent 和组织能力

先提供稳定、版本化的 REST／事件接口与会议级令牌，再写 Hermes Skill；MCP 可作为相同权限体系上的适配。补事件发现、附件索引、同步状态、撤销、费用／调用配额和操作记录。之后再扩展细致个人空间、更多协作角色与复杂模型编排。

首轮不用同时做完整 OAuth 体系、所有 Agent 适配器和庞大的名人库。一个内部工作区、可靠的服务器记录、人类可直接使用的界面和可授权的 Agent 通道，就可以支持早期同事试用。

## 10. 后续必须补的真实验收

这些是后续开发与凭据就绪后的验收目标，不是本次已通过的结果：

1. 内部会议：会前写“预算 12 万、至少三周”，会中提出“14 万、一周”，AI 在工作分配前明确指出冲突，并能引用约束。
2. 客户谈判：客户询问未支持功能，AI 给出可说出口的事实回答，提示不能承诺的内容，标出出处和待核实项。
3. 实际 GPT／Claude：使用已授权网关验证模型可用、首条有用建议、完整回答与失败切换，分别记录真实耗时；本机模拟耗时没有参考价值。
4. 真音频：多个说话人、中文夹杂技术名词、噪声、长会、断网及权限恢复；验证不会静默漏段或误归属。
5. 恢复：刷新、总结返回、后端重启、断线后补拉，所有原稿、修订和 AI 建议一致；长会不删原文。
6. 同步与授权：人类和真实 Hermes 同时参与，写入及时可见，重复事件不重复，超出授权范围被拒绝，撤销立即生效。
7. 私有边界：展示版页面与客户版导出不含我方策略／底线；私有建议仍可回溯到原记录。

建议先确定上述首轮范围，再进入开发。此次没有改动任何产品实现，也没有部署。
